# 前端消息类型与处理规范

本文档面向 APP / H5 前端，说明消息发送、历史拉取和 WebSocket 推送中的类型、结构与处理规则。

协议定义以 `contracts/proto/chat/message.proto` 为准，HTTP 字段以 API Gateway 返回为准。

## 1. 前端先记住这些规则

| 规则 | 前端处理 |
| --- | --- |
| WebSocket 外层 `type` 有两种类型 | 字符串表示消息流事件，数字表示个人实时通知 |
| 聊天消息类型使用数字 | 按 `message.type` 选择气泡组件，不按 `body` 猜类型 |
| `body` 语义上只有一个有效内容 | HTTP JSON 可能同时返回所有 Body 字段，未使用字段为 `null` |
| `system.text` 只用于兜底展示 | 业务判断必须使用数字 `type` 和 `system.event_type` |
| 会话消息有 `msg_id + msg_seq` | 参与历史、排序、未读数和断线补拉 |
| 个人通知有 `event_id` | 不写消息表，不增加未读数，按 `event_id` 去重 |
| 编辑和删除走独立更新流 | 不增加 `msg_seq`，使用 `update_seq` 单独同步 |
| HTTP 的 `uint64` 返回字符串 | `msg_seq`、`size_bytes` 等在 HTTP 中按字符串解析 |
| WebSocket 序号当前是数字 | 前端内部建议统一转成字符串或安全整数类型 |
| 未知类型必须容错 | 保留消息位置，显示“暂不支持的消息类型”，不能让整批消息解析失败 |

推荐的 WebSocket 分发逻辑：

```ts
function handleSocketPacket(packet: unknown) {
  if (!packet || typeof packet !== "object") return

  const data = packet as { type?: string | number }
  if (typeof data.type === "number") {
    handleUserNotification(data)
    return
  }

  switch (data.type) {
    case "message.batch":
      handleMessageBatch(data)
      break
    case "message.multi_batch":
      for (const conversation of data.conversations ?? []) {
        handleMessageBatch({ type: "message.batch", ...conversation })
      }
      break
    case "message.sync":
      pullConversationGap(data)
      break
    case "message.update":
      handleMessageUpdate(data)
      break
    case "message.update.batch":
      handleMessageUpdateBatch(data)
      break
  }
}
```

## 2. WebSocket 外层结构

前端会收到六类 Envelope：

| 外层 `type` | 用途 | 是否带消息正文 | 断线补偿 |
| --- | --- | --- | --- |
| `message.batch` | 会话消息实时推送 | 是，`messages[]` | `/v1/message/pull` 或 `/v1/message/batch-pull` |
| `message.multi_batch` | 一次群发命中多个会话时的合并实时推送 | 是，`conversations[].messages[]` | 按每个会话分别补拉 |
| `message.sync` | 降级同步提示 | 否 | 必须按 `latest_msg_seq` 补拉 |
| `message.update` | 消息编辑或删除 | 在 `metadata.message` 中按场景携带 | `/v1/message/update/pull` |
| `message.update.batch` | 批量删除产生的消息更新 | 在 `updates[]` 中按项携带 | `/v1/message/update/pull` |
| 数字，例如 `1200` | 个人实时通知 | `body.system` | 通过对应业务接口重新查询最终状态 |

### 2.1 `message.batch`

```json
{
  "type": "message.batch",
  "conversation_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a1001",
  "latest_msg_seq": 24,
  "degraded": false,
  "messages": [
    {
      "msg_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a2001",
      "msg_seq": 24,
      "sender_id": "24136291013",
      "type": 101,
      "body": {
        "text": {
          "text": "你好"
        }
      },
      "mentions": [],
      "entities": []
    }
  ],
  "server_time": "2026-07-26T12:00:00Z"
}
```

`messages[]` 是实时推送精简结构，只保证以下字段：

| 字段 | 说明 |
| --- | --- |
| `msg_id` | 服务端消息 ID，消息去重主键 |
| `msg_seq` | 会话内递增序号 |
| `sender_id` | 发送人用户 ID |
| `type` | 数字消息类型 |
| `body` | 消息内容 |
| `mentions` | 消息级 @ 信息，可能省略 |
| `entities` | 文本范围实体，可能省略 |

处理顺序：

1. 按 `conversation_id + msg_seq` 排序。
2. 按 `msg_id` 或 `conversation_id + msg_seq` 去重。
3. 如果收到的 `msg_seq` 大于本地序号加一，调用消息拉取接口补缺口。
4. 保存本次 `latest_msg_seq`，不要只依赖 `messages[]` 最后一项。

### 2.2 `message.multi_batch`

`/v1/message/batch-send` 会在每个目标会话中分别创建消息。如果同一在线设备同时属于多个目标会话，Push Gateway 将这些消息放进一个 WebSocket 帧：

```json
{
  "type": "message.multi_batch",
  "batch_id": "local-batch-001",
  "conversations": [
    {
      "conversation_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a1001",
      "latest_msg_seq": 25,
      "degraded": false,
      "messages": [
        {
          "msg_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a2002",
          "msg_seq": 25,
          "sender_id": "24136291013",
          "type": 101,
          "body": {"text": {"text": "统一发送的内容"}}
        }
      ]
    },
    {
      "conversation_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a1002",
      "latest_msg_seq": 8,
      "degraded": false,
      "messages": [
        {
          "msg_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a2003",
          "msg_seq": 8,
          "sender_id": "24136291013",
          "type": 101,
          "body": {"text": {"text": "统一发送的内容"}}
        }
      ]
    }
  ],
  "server_time": "2026-07-30T12:00:00Z"
}
```

处理时遍历 `conversations[]`，把每一项交给现有 `message.batch` 处理函数。不同会话的消息事实没有合并：每项仍有独立的 `conversation_id`、`msg_id` 和 `msg_seq`。同一设备只减少 WebSocket 帧数，不能跨会话去重消息。

### 2.3 `message.sync`

```json
{
  "type": "message.sync",
  "conversation_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a1001",
  "latest_msg_seq": 105,
  "degraded": true,
  "server_time": "2026-07-26T12:00:00Z"
}
```

收到后不要等待正文推送，直接从本地最后连续序号开始调用 `/v1/message/pull`。`message.sync` 可能由大群或推送压力降级触发，不表示消息丢失。

### 2.4 数字类型个人通知

```json
{
  "type": 1200,
  "event_id": "application_id",
  "body": {
    "system": {
      "event_type": "friend_application_created",
      "text": "请求添加你为好友",
      "extra": {
        "application_id": "application_id",
        "requester_id": "requester_user_id",
        "target_id": "target_user_id"
      }
    }
  },
  "server_time": "2026-07-26T12:00:00Z"
}
```

处理规则：

- 使用 `event_id` 去重。
- 使用数字 `type` 选择业务模块。
- 使用 `body.system.event_type` 区分同一数字类型下的具体动作。
- `body.system.extra` 的值统一按字符串读取。
- 个人通知只投递在线设备，不写会话消息表。
- 用户离线时，通过好友申请、群申请、通话记录、好友列表或会话同步接口重新获取最终状态。

### 2.5 `message.update`

```json
{
  "type": "message.update",
  "conversation_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a1001",
  "event_type": "message.edited",
  "metadata": {
    "event_id": "event_id",
    "update_id": "update_id",
    "update_seq": 8,
    "update_type": 1,
    "target_msg_id": "msg_id",
    "operator_user_id": "user_id",
    "delete_scope": 0,
    "message": {
      "msg_id": "msg_id",
      "type": 101,
      "body": {
        "text": {
          "text": "修改后的内容"
        }
      },
      "version": 2,
      "edited_at": "2026-07-26T12:00:00Z"
    }
  },
  "server_time": "2026-07-26T12:00:00Z"
}
```

| 字段 | 说明 |
| --- | --- |
| `event_type` | `message.edited` 或 `message.deleted` |
| `metadata.update_id` | 更新事件去重 ID |
| `metadata.update_seq` | 会话内独立更新序号 |
| `metadata.target_msg_id` | 被修改的原消息 ID |
| `metadata.update_type` | `1` 编辑，`2` 删除 |
| `metadata.delete_scope` | `1` 仅自己，`2` 所有人；编辑时为 `0` |
| `metadata.message` | 编辑后或全局删除后的消息快照；仅自己删除时为空 |

前端按 `target_msg_id` 更新原消息，不新增聊天气泡。断线后使用 `/v1/message/update/pull`，并分别保存 `last_msg_seq` 与 `last_update_seq`。

单条删除使用 `/v1/message/update`，批量删除使用 `/v1/message/batch-delete`。批量删除最多包含同一会话的 100 条消息，每个目标消息仍持久化独立的更新记录和 `update_seq`，但实时推送合并为一个 `message.update.batch` WebSocket 帧。

### 2.6 `message.update.batch`

```json
{
  "type": "message.update.batch",
  "conversation_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a1001",
  "batch_id": "local-batch-delete-001",
  "latest_update_seq": 10,
  "event_type": "message.updates.batch",
  "updates": [
    {
      "update_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a3001",
      "update_seq": 9,
      "update_type": 2,
      "target_msg_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a2001",
      "operator_user_id": "24136291013",
      "delete_scope": 2,
      "message": {
        "msg_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a2001",
        "status": 5,
        "version": 2
      }
    },
    {
      "update_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a3002",
      "update_seq": 10,
      "update_type": 2,
      "target_msg_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a2002",
      "operator_user_id": "24136291013",
      "delete_scope": 2,
      "message": {
        "msg_id": "019ef02a-4b45-7d3d-9d67-1cf19a9a2002",
        "status": 5,
        "version": 2
      }
    }
  ],
  "server_time": "2026-08-02T12:00:00Z"
}
```

`updates[]` 中每项的字段语义与单条 `message.update.metadata` 相同。前端逐项按 `update_id` 去重，再复用现有消息更新函数按 `target_msg_id` 修改或移除本地消息。`scope=self` 时整帧只发给执行人设备，`scope=all` 时发给会话内在线用户。

`latest_update_seq` 只表示此实时帧内的最大更新序号。WebSocket 可能丢失或乱序，因此不能用它直接覆盖本地持久化补拉游标；持久化游标仍只根据 `/v1/message/update/pull` 返回的 `next_update_seq` 推进。

更完整的编辑删除说明见 [前端消息编辑删除对接说明.md](./前端消息编辑删除对接说明.md)。

## 3. HTTP 完整消息对象

发送响应和历史拉取返回完整 `Message`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `msg_id` | `string` | 服务端消息 ID |
| `conversation_id` | `string` | 所属会话 ID |
| `msg_seq` | `string` | 会话内递增序号 |
| `sender_id` | `string` | 发送人或系统事件业务主角用户 ID |
| `client_msg_id` | `string` | 客户端发送幂等 ID |
| `type` | `number` | 消息类型数字 |
| `status` | `number` | `1` 发送中，`2` 成功，`3` 失败，`5` 已删除 |
| `body` | `object` | 与 `type` 对应的内容 |
| `version` | `string` | 内容版本，首次为 `1`，编辑后递增 |
| `edited_at` | `string` | 最后编辑时间，未编辑时为空 |
| `mentions` | `array` | 消息级 @ 目标 |
| `entities` | `array` | 文本范围实体，结构为 `type/offset/length/preset_id` |
| `sent_at` | `string` | 服务端发送时间，RFC 3339 |
| `updated_at` | `string` | 最后更新时间，RFC 3339 |
| `expire_at` | `string` | 自动删除时间，为空表示不自动删除 |

HTTP `body` 当前会返回完整字段集合，只有一个字段非 `null`：

```json
{
  "text": {
    "text": "你好"
  },
  "image": null,
  "file": null,
  "audio": null,
  "video": null,
  "system": null,
  "card": null,
  "custom": null,
  "typing": null,
  "quote": null,
  "emoji": null,
  "transfer": null,
  "red_packet": null
}
```

前端只读取 `type` 对应字段。请求发送时也只能传一个非空 Body 字段。

### 5.2 消息级 @

文本、图片、视频、文件和引用等普通消息都可以在 Body 外携带 `mentions`：

| 字段 | 说明 |
| --- | --- |
| `mentions[].type` | `user` 表示指定用户，`all` 表示所有人 |
| `mentions[].user_id` | `type=user` 时必填，`type=all` 时为空 |
| `mentions[].nickname` | 前端传入的展示昵称 |

```json
{
  "conversation_id": "conversation_id",
  "client_msg_id": "local-002",
  "body": {
    "text": {
      "text": "@所有人 明天开会"
    }
  },
  "mentions": [
    {
      "type": "all",
      "user_id": "",
      "nickname": "所有人"
    }
  ]
}
```

@ 不使用独立消息类型，统一由普通 Body 加消息级 `mentions` 表示。

### 5.3 消息实体

普通消息可以在 Body 外携带 `entities`，用于描述文本中的范围信息：

| 字段 | 说明 |
| --- | --- |
| `entities[].type` | 实体类型 |
| `entities[].offset` | 在文本中的起始偏移量，从 `0` 开始 |
| `entities[].length` | 实体覆盖的文本长度，必须大于 `0` |
| `entities[].preset_id` | 预设资源 ID；当前类型不需要时传空字符串 |

```json
{
  "conversation_id": "conversation_id",
  "client_msg_id": "local-003",
  "body": {
    "text": {
      "text": "你好"
    }
  },
  "entities": [
    {
      "type": "preset",
      "offset": 0,
      "length": 2,
      "preset_id": "preset_id"
    }
  ]
}
```

单条发送、批量发送和消息编辑都支持 `entities`。转发时服务端忽略前端提交的实体，直接继承源消息的 `entities`；HTTP 历史拉取、编辑更新和 WebSocket 推送使用同一结构。

### 5.4 单条与批量转发

转发不新增消息类型，服务端复制源消息内容，并在消息顶层返回来源：

```json
{
  "forward_origin": {
    "type": "user",
    "user_id": "原消息发送者用户ID",
    "name": "原消息发送者昵称",
    "avatar_url": "原消息发送者头像URL"
  }
}
```

普通转发调用 `/v1/message/send`，传 `conversation_id`、`client_msg_id` 和 `source_msg_id`。批量场景分为两种：

| 场景 | 接口 | 语义 |
| --- | --- | --- |
| 一条消息转发到多个目标 | `/v1/message/batch-send` | 一个 `source_msg_id`，多个 `targets` |
| 多条消息转发到一个会话 | `/v1/message/batch-forward` | 一个 `conversation_id`，多个 `items[].source_msg_id` |

`/v1/message/batch-forward` 按 `items[]` 输入顺序逐条创建消息，最多 100 条，然后发送可选的 `comment` 补充文字。每条转发消息保留源消息自己的 `type/body/entities` 和 `forward_origin`，并获得独立的 `msg_id/msg_seq/client_msg_id`；comment 是当前用户发送且不带 `forward_origin` 的普通文本消息。目标设备收到一个 `message.batch`，`messages[]` 中转发消息在前、comment 在最后；全部转发失败时 comment 不发送。

转发请求不需要传 `body`，来源信息也不能由客户端填写。

- 来源始终指向最初发送者；再次转发不会改成中间转发人。
- 服务端校验当前用户能够查看源消息，客户端不能自行填写来源。
- 接收方不会拿到源会话 ID 和源消息 ID。
- HTTP 拉取会把来源用户加入 `users` 并补充 `name` 和 `avatar_url`；WebSocket 以 `forward_origin.user_id` 为稳定标识，展示资料为空时从本地用户资料缓存解析。
- 转发消息不能编辑，可以按现有规则删除。
- 当前支持文本、图片、语音、视频、文件、@、名片、位置、自定义、表情和 Markdown；输入状态、系统通知和引用消息不允许直接转发。引用消息需要先解除源会话引用关系后再设计跨会话展示。

### 5.5 其他 Body

| Body | 字段 | 说明 |

特殊规则：

- `1503` 是个人通知，只发给群主和拥有入群审核权限的管理员。
- `1508` 同时走两条链路：正常成员收到群会话消息；被移除用户收到无会话 ID 的个人通知。
- `member_user_ids` 当前是逗号分隔字符串，前端按 `,` 拆分。
- 群名称、群头像、群简介和群公告分别写入独立消息。一次请求同时修改多项时，前端会收到多条不同 `type/event_type` 的群消息。
- `1502/group_info_changed` 在群资料更新场景仅表示群头像变更；群简介必须使用 `1521/group_description_changed`。
- 前端根据 `type/event_type` 选择文案模板，使用 `operator_nickname` 和对应的新值填充，不解析或拼接 `system.text`。
- 收到 `1519` 后刷新群资料；展示公告后将对应的 `announcement_version` 提交到 `POST /v1/group/announcement/read`，不要直接在本地清除新版本的未读状态。

`group_member_left` 的 `extra` 示例：

```json
{
  "group_id": "45132520337",
  "user_id": "28822365089",
  "member_user_id": "28822365089",
  "clear_history": "true",
  "clear_before_seq": "1024"
}
```

- `clear_history` 和 `clear_before_seq` 位于 `system.extra`，受现有结构约束均为字符串。
- `clear_history=true` 时，删除本地满足 `sender_id == member_user_id && msg_seq <= clear_before_seq` 的消息。
- 清理范围只包含用户内容消息 `type=101..115`，群事件、通话事件等系统消息必须保留。
- 客户端必须持久化该删除水位；之后晚到的创建、编辑或同步事件落在该范围内时直接忽略，避免异步旧事件恢复已删除消息。
- `clear_history=false` 时只处理退群和成员列表变化，不清除历史发言。

### 6.4 会话清空 `2102`

```json
{
  "type": 2102,
  "event_id": "operation_id:conversation_cleared",
  "body": {
    "system": {
      "event_type": "conversation_cleared",
      "text": "聊天记录已清空",
      "extra": {
        "conversation_id": "conversation_id",
        "operator_user_id": "user_id",
        "clear_before_seq": "120",
        "scope": "both"
      }
    }
  },
  "server_time": "2026-07-26T12:00:00Z"
}
```

前端动作：

1. 找到 `conversation_id` 对应的本地会话。
2. 删除或隐藏 `msg_seq <= clear_before_seq` 的本地消息。
3. 将未读数归零。
4. 单聊没有更新消息时，从普通会话列表隐藏该会话，后续出现新消息时恢复。
5. 群聊保留会话入口，将 `last_message` 清空并把未读数归零。

## 7. 拉取与本地游标

| 场景 | 使用接口 | 本地保存 |
| --- | --- | --- |
| 单会话消息缺口 | `/v1/message/pull` | `last_msg_seq` |
| 多会话重连补拉 | `/v1/message/batch-pull` | 每个会话的 `last_msg_seq` |
| 编辑删除缺口 | `/v1/message/update/pull` | `last_update_seq` |
| 多条消息逐条转发 | `/v1/message/batch-forward` | 每条消息及可选 comment 使用独立的 `client_msg_id` |
| 好友申请通知丢失 | 好友申请列表接口 | 申请状态和未读数 |
| 入群申请通知丢失 | 群申请审核列表接口 | 申请状态 |
| 通话过程通知丢失 | `/v2/call/list`、`/v1/call/detail` | 最终通话状态 |

普通消息流和更新流必须分开维护：

- `last_msg_seq` 只表示聊天消息进度。
- `last_update_seq` 只表示编辑和删除进度。
- 收到更大的游标但缺少中间项时，先补拉，再推进本地连续游标。

## 8. 前端实现清单

- [ ] WebSocket 外层 `type` 同时支持字符串和数字。
- [ ] 支持 `message.batch`、`message.multi_batch`、`message.sync`、`message.update`、`message.update.batch` 五种字符串 Envelope。
- [ ] `message.update.batch` 遍历 `updates[]`，逐项按 `update_id` 去重并复用单条更新处理逻辑。
- [ ] 数字个人通知按 `event_id` 去重。
- [ ] 聊天消息按 `msg_id` 和 `conversation_id + msg_seq` 去重。
- [ ] HTTP `uint64` 字符串和 WebSocket 数字统一转换。
- [ ] `body` 只读取数字 `type` 对应的非空字段。
- [ ] 未知数字类型使用兜底气泡，不中断消息列表。
- [ ] `system.text` 不参与业务判断。
- [ ] `message.sync` 或 `degraded=true` 立即触发补拉。
- [ ] 分开保存 `last_msg_seq` 和 `last_update_seq`。
- [ ] `1202` 关闭好友发送入口，`2102` 清理本地历史。
- [ ] `1508` 被移除用户关闭群页面并移除群会话入口。
- [ ] 通话通知离线恢复使用通话记录接口，不依赖过程通知完整到达。

## 9. 推荐媒体格式

上传接口允许多种扩展名，但聊天展示建议统一格式：

| 类型 | 推荐格式 | 编码 |
| --- | --- | --- |
| 普通图片 | `jpg` | JPEG |
| 透明图片 | `png` | PNG |
| 图片缩略图 | `webp` 或 `jpg` | WebP / JPEG |
| 语音 | `m4a` | AAC-LC，单声道，16-24kHz，32-48kbps |
| 视频 | `mp4` | H.264/AVC + AAC-LC，`yuv420p`，`faststart` |

`heic/heif`、`mov`、`mkv`、`webm` 可以作为上传输入，但正式展示链路应转换成兼容格式。IM 消息只保存媒体 ID、URL、尺寸、大小和时长等元数据，不通过消息链路传输二进制文件。
